## What could not be enforced or tested locally, and why

- **This session ran from the PitchCraft repo**, so PitchCraft's guard checked every git command it ran. That guard correctly blocked three things:
  - `git config core.hooksPath .githooks`: changing hooksPath is blocked in any repo. **Daniel enables the hooks** (below).
  - `git push origin dev`: PitchCraft only allows `v2` and `experiment/*`. **The push of this unit is done by Daniel, or by a session opened in this repo**, where the new guard allows `dev`.
  - The real-git tests of a forced push, a push to `main`/`feature/x`/a tag, a deletion and a foreign `--author`: they were blocked before git ran. They are covered by the fed-input layer instead.
- **Hooks are opt-in per clone.** Git never activates versioned hooks on its own. A clone without `core.hooksPath` has no local hooks, and anyone can bypass them with `--no-verify`. The agents are forbidden from doing either (guard and deny rules), but only GitHub's rulesets bind everyone.
- **The guard does not see** a script file that runs git, a shell alias or function, or git inside a PowerShell script block or parentheses (same limits as PitchCraft, listed in its docstring). The git hooks and the rulesets cover those.
- **The deny rules are prefix matches.** They catch the plain spellings (`git push --force ...`). Reordered or wrapped spellings (`git push origin dev --force`, `bash -c "..."`) are caught by the guard, not by the deny rules.
- **Codex** has no PreToolUse equivalent here. It is bound by AGENTS.md and by the git hooks (once enabled in the clone it uses) and the rulesets.
- **The guard needs Python** on the machine that runs Claude Code (it was 3.14 here). This adds no npm dependency, and CI does not run the guard tests.

## What Daniel must configure

**Locally, once per clone** (in `C:\Dev\danielherdenez-site`):

```
git config core.hooksPath .githooks
git config --get core.hooksPath   # must print .githooks
```

**In GitHub** (Settings → Rules → Rulesets), after the first `ci` run on `dev` so the check name exists:

1. **Ruleset `main`** (target: branch `main`, enforcement Active, no bypass actors):
   - Restrict deletions.
   - Block force pushes.
   - Require a pull request before merging (0 approvals is fine; only Daniel merges). Allowed merge method: "Merge" (keeps `dev` fast-forwardable from `main`).
   - Require status checks to pass: add `ci` (source GitHub Actions). Tick "Require branches to be up to date before merging".
2. **Ruleset `dev`** (target: branch `dev`, enforcement Active):
   - Restrict deletions.
   - Block force pushes.
   - Do not require a PR or checks on `dev`: the agents push to it directly, and `ci` runs on every push.
3. **Optional, recommended:** a tag ruleset on `**` (all tags) with "Restrict creations, updates, deletions", since tags are off-limits to the agents.
4. **Optional:** give the agent sessions a fine-grained token without `administration` write, so `gh` cannot edit rulesets.
